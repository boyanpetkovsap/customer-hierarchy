Customer Hierarchy Selector

A page-level control that lets a user switch the company entity in focus — viewing data for the global parent or any subsidiary their account can access — without changing the filters on individual tables, cards, or charts.

Pattern Canonical: page level Density: Cozy

Overview

Customer Hierarchy is the ability of a user who is signed in to an account on SAP for Me to view and filter data for different subsidiaries of their company. For example, an IT administrator signed in to a [customer_ID] Global account can also see and filter data for [customer_ID] Germany or [customer_ID] China.

The Customer Hierarchy Selector exposes that capability as a single control in the page header. The selected entity becomes the context for the entire page: every table, card, and chart reflects the same subsidiary. The user sets the context once instead of repeating the same selection across each element on the page.

Scope Hierarchy

Customer Hierarchy filtering is not a single widget — it is a scoped capability that can live at different levels of the interface. Teams have independently built their own versions at different levels, producing an inconsistent experience. This section defines the canonical level, and marks the others as deprecated or temporary.

The three scope levels

LevelWhere it appearsSelection persists?Status
Page In the Dynamic Page Header, in the title area Yes — across all content on the page Canonical
Tab / Dashboard In a tab header or dashboard-level toolbar No — resets on navigation Temporary workaround
Card / Table In a single card header or table toolbar No — isolated to that element Deprecated

The canonical pattern: page level

The Customer Hierarchy Selector belongs in the Dynamic Page Header, directly after the page title and separated by a pipe character:

Business AI |

This placement means:

  • The selected entity applies to all data on the current page.
  • Users set the context once; every table, card, and chart updates together.
  • The current context stays visible at all times, without scrolling.
Why this level? The page header is the only element permanently visible during a session on a page. Placing the selector here signals that the entity is a context governing the whole view — not a filter on one dataset.

When page level is not yet available

If a page does not yet use a Dynamic Page Header that supports the title-embedded selector, a tab-level or dashboard-level control is acceptable as a temporary implementation, provided it is flagged for migration. Card-level and table-level controls must not be introduced in new features.

Migration priority

Current implementationRecommended actionPriority
Tab-level switch (e.g. GBOITPACS-10616)Migrate to page-level selector; remove tab controlHigh
Table toolbar filterRemove; rely on page-level selectionHigh
Card header filterRemove once page-level exists on that pageMedium
No switching at allAdd page-level selector if the page surfaces entity-scoped dataLow

Anatomy

The selector is composed inside the Title Area of the Dynamic Page Header. It is not a standalone component — it is an interactive element within the header title.

Closed state

2SeparatorA pipe character ( | ) connecting the title to the entity. Rendered as part of the title string.

The trigger (3–4) uses a bottom-border-only treatment on a white background, so it reads as an inline interactive element rather than a standalone form field.

Open state

Clicking the entity name or chevron opens a Popover below the trigger, hosting a single-column list of accessible entities (SAP Drop-Down, Cozy density, 40px items).

Behavior

Default state

  • Multiple entities: the selector shows the top-level entity (e.g. [customer_ID] Global) and is interactive.
  • Single entity: the entity name is shown as plain text — no chevron, no dropdown. The control degrades gracefully.
  • No entity context: only the page title is shown, with no separator or entity name.

Interaction flow

  1. User clicks the entity name or chevron.
  2. A Popover opens, anchored below the trigger.
  3. The Popover lists the subsidiaries the account can access.
  4. User selects a subsidiary.
  5. The Popover closes and the header updates to the selected entity.
  6. All data on the page refreshes to the selected entity's scope.
  7. The selection persists for the session on this page.

Scope of effect

Changing the entity updates every data element on the page — all tables, charts, and cards. There is no partial update. If an element cannot support hierarchy filtering (e.g. it only shows global data), it must surface an informational message rather than silently show mismatched data.

Persistence rules

ScenarioBehavior
Navigating between sections/tabs on the same pageSelection persists
Navigating to a different page / dashboardSelection resets to the account default
Refreshing the browserSelection resets to the account default
Opening the same page in a new tabEach tab has an independent selection
Open decision for the team. Should the selection persist across pages within a session? The current design resets per page, but research suggests cross-page persistence would cut friction. Resolve this before teams implement the page-level selector at scale.

Empty state

If the account has no subsidiaries, do not render the selector at all. Show the page title alone — no separator, no trigger, no disabled placeholder.

Don't repeat the switch on each table and card — users must set it four times.

Use the selector when…

ConditionRationale
The page surfaces data scoped to a company entityThe selector shows which entity the data belongs to and lets the user change it in place
The account can access two or more subsidiariesThe selector only adds value when there is a real choice
The page has multiple elements that should share one entityOne page-level control is far less friction than per-element switches
The feature is built on a Dynamic Page HeaderThat is the only correct placement for this pattern

Do not use the selector when…

ConditionWhat to do instead
The account has only one entityHide the selector; show only the page title
The data is always global, never entity-scopedDon't add a selector; make the global scope clear in the page context
Only one card or table supports entity filteringUse a column- or toolbar-level filter on that element; don't imply page-wide scope
You are building a new per-card or per-table switchThis is deprecated — use the page-level selector or escalate to UX

Screen reader announcement on change

When a new entity is selected and the page refreshes, a live region must announce the change — otherwise screen reader users get no signal that all content updated.

<div role="status" aria-live="polite" aria-atomic="true" class="sr-only">
  <!-- injected on selection -->
  Showing data for [customer_ID] Germany. Page content updated.
</div>

Use polite, not assertive, so the announcement does not interrupt active reading.

Focus management

After selection, focus must return to the trigger — not the top of the page — so keyboard users can keep working from where they were.

Color & contrast

Entity text (#131e29 on white) meets WCAG AA at 14px. The chevron (#758ca4) is decorative. Because the trigger relies on a bottom border for its affordance, confirm a non-color cue (border, focus ring) is visible in all themes, including high-contrast — per WCAG 1.4.1.
